# 코레일 취소표·예약대기 API 감시봇 v9 — 나주 출발

**2026년 10월 24일(토), 성인 1명 / 나주 → 서울·용산·수서 / KTX·KTX-산천**

기존 공식 웹사이트 Playwright 방식 v8은 Railway에서 `-8202`(데이터센터 접속 제한) 오류가 나타났습니다. 이 버전은 공식 웹사이트의 DOM을 읽는 대신, 앞서 사용했던 **비공식 코레일+ Python API 클라이언트**로 조회합니다. **이것이 코레일의 데이터센터 차단을 우회하거나 해제한다는 뜻은 아닙니다.** API 접속 역시 제한될 수 있으므로, 명시적 거부 시 알림 후 종료합니다.

## 감시 조건 (v8 승계)

| 항목 | 설정 |
|---|---|
| 날짜 | 2026-10-24(토), 00:00부터 검색 |
| 출발역 | **나주** |
| 도착역 | 서울·용산·수서 |
| 대상 | **KTX / KTX-산천**, 출발시각순 최대 **10편** |
| 인원 | 어른 1명 |
| 알림 ① | 일반실 또는 특실 좌석 **즉시 예매 가능** (`reservation_code == '11'`) |
| 알림 ② | **예약대기 신청 가능** (`wait_reservation_flag == ' 9'` 등) |
| 알림 제외 | 456편(시각 불문), 무궁화·ITX, 입석·입석+좌석·자유석 |
| 재조회 | 20~30초 사이 무작위 (스캔 시작 간격 목표) |
| 종료 | 2026-10-25 00:00 KST |

열차 목록은 기존 v8에서 **KTX 탭을 눌렀을 때 보이는 첫 10편**을 근사합니다. 이 비공식 API에는 웹의 '서울·용산·수서 함께 보기' 1회 호출과 동일한 기능이 **검증되어 있지 않아**, **나주→서울 / →용산 / →수서**를 각각 조회하고 결과를 합칩니다. API에 반환된 KTX를 출발시각순으로 정렬하여 **최초 10편만 감시**한 다음 456편을 제외합니다. 이는 웹 첫 화면과 정확히 일치한다고 보장하지 않습니다. **첫 10편에 포함되지 않은 오후 열차는 알림이 오지 않습니다.** 출발한 열차는 자동으로 대상에서 빠집니다.

한 번의 감시에서 최소 3번(도착역 3곳) API를 호출하고 페이지가 더 있으면 최대 `3 × MAX_PAGES_PER_ROUTE`회 호출합니다. 기본값 4면 최대 12회입니다. 20~30초는 API 단일 호출 간격이 아니라 감시 시작 간격입니다. 과도한 요청으로 인해 이용 제한이 발생할 수 있습니다.

## 상태 판별

- 일반 좌석: 일반실/특실 예약 가능 코드가 **`11`**이고, 상태 문구에 입석·예약대기·매진 등의 배제 단어가 없어야 합니다. 표시 운임만으로 판단하지 않습니다.
- 예약대기: 서버의 `wait_reservation_flag == ' 9'`(공백 제거 후 `9`) 또는 명시적인 `예약대기` 상태 표시. 좌석 확보나 발권이 아닙니다.
- 456편: 출발시간이 바뀌어도 열차번호로 제외합니다.
- 조회 행 누락·코드 불명: 빈자리로 추정하지 않습니다.
- 세 노선 중 **페이지 조회가 불완전**하면 첫 10편을 확정할 수 없으므로 **알림과 상태 갱신을 보류**합니다.
- 좌석/예약대기가 열렸을 때 알리고, 계속 열려 있으면 중복 알림을 보내지 않습니다. 다시 닫힌 뒤 열리면 새 알림을 보냅니다.
- 로그인·자동 예매·결제·예약대기 신청·CAPTCHA 우회·프록시/IP 전환은 없습니다.

## Railway 배포

1. ZIP을 **압축 해제**한 후 모든 파일을 기존 코레일 감시 GitHub 저장소의 **최상위 폴더**에 업로드하고 Commit합니다. `watcher.py`, `monitor.py`, `Dockerfile`, `requirements.txt`, `railway.json` 등이 포함되어야 합니다. **기존 v8과 동시 실행하지 마세요.**
2. Railway에서 해당 GitHub 저장소에 연결된 서비스가 자동 재배포되었는지 확인합니다.
3. **Variables**는 기존 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`를 그대로 사용합니다.
4. `POLL_MIN_SECONDS=20`, `POLL_MAX_SECONDS=30`는 기본값이라 설정하지 않아도 됩니다. `MAX_TRAINS=10`, `MAX_PAGES_PER_ROUTE=4`도 기본값입니다.
5. Deploy Logs에 `코레일 나주→서울·용산·수서 KTX API 감시 v9 시작`이 표시되는지 확인합니다. 시작 텔레그램이 오더라도 **조회 성공과는 별개**입니다.
6. `#1: KTX첫목록 ... API요청=... / 페이지불완전=-`와 각 열차 로그를 확인하세요. 실제 라이브러리와 코레일 서버 간 동작은 아직 검증되지 않았습니다.

**이전 Playwright v8의 환경변수 중 `REFRESH_MODE`는 이 버전에서 사용하지 않습니다.**

주요 선택 환경변수:

| 환경변수 | 기본값 | 설명 |
|---|---:|---|
| `POLL_MIN_SECONDS` | `20` | 감시 간격 최소 (초) |
| `POLL_MAX_SECONDS` | `30` | 감시 간격 최대 (초) |
| `MAX_TRAINS` | `10` | 출발순 감시 편수 (1~50) |
| `MAX_PAGES_PER_ROUTE` | `4` | 노선별 조회 페이지 상한 (1~8) |
| `HEARTBEAT_MINUTES` | `60` | 정상 작동 텔레그램 확인 주기. `0`이면 비활성화 |
| `LOG_DETAIL_EVERY` | `10` | 상세 열차 목록 로그 주기 |
| `STATE_FILE` | `state_naju_v9.json` | 중복 알림 방지용 JSON 경로 |

Railway Volume을 추가한다면 `STATE_FILE=/data/state_naju_v9.json`으로 저장하면 재배포 간 알림 상태를 유지할 수 있습니다. Volume이 없으면 재배포 시 알림 중복 가능성이 있습니다.

## 오류 대응

- **`-8202` / VPN·데이터센터 거부**: 텔레그램으로 차단 경고를 시도한 후 **즉시 종료**, 재시도하지 않음.
- **코레일 명시적 호출 제한**(HTTP 403/429, `BT019`, `BT023` 등): 5분, 10분 대기 후 세 번째 연속 거부 시 종료. 우회 없음.
- 그 밖의 네트워크/서버 오류: 1분부터 최대 15분 지수형 재시도. 3회 오류 또는 5분 이상 정상 조회 없음 시 알림.
- 한 노선이라도 페이지 불완전: 3회 지속 시 Telegram 알림, 이후 60초 이상 간격으로 조회.
- 프로그램은 한국시간 **2026-10-25 00:00**에 자동 종료. 종료된 정상 프로세스는 `railway.json`에서 `ON_FAILURE` 재시작만 허용하므로 자동 재시작되지 않음.
